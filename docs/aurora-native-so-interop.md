# Нативная `.so` и Kotlin/Native Interop на Aurora

Эта страница описывает конкретную проверку в демо: как C-библиотека собирается для Aurora, попадает в RPM и вызывается из Kotlin/Native. Это пример C ABI, а не JNI и не загрузка Kotlin-библиотеки на JVM.

## Общая схема

```text
Экран «Проверка библиотек» → Kotlin actual → cinterop-обёртка
→ dlopen(.so) → dlsym(aurora_interop_probe) → функция C
→ заполненная C-структура → проверки Kotlin → журнал
```

Нативная библиотека и приложение поставляются в **одном RPM**, но `.so` остаётся отдельным файлом. При сборке в исполняемый файл включается сгенерированная cinterop-обёртка; сама библиотека загружается динамически только при нажатии кнопки проверки.

## Какие файлы за что отвечают

| Файл | Назначение |
| --- | --- |
| `composeApp/native-interop/interop_probe.h` | Структура результата, сигнатура C ABI и inline-обёртка динамической загрузки. |
| `composeApp/native-interop/interop_probe.c` | Реализация экспортируемой функции `aurora_interop_probe` в `.so`. |
| `composeApp/src/nativeInterop/cinterop/interop_probe.def` | Заголовок и пакет Kotlin, из которых cinterop генерирует биндинги. |
| `composeApp/build.aurora.gradle.kts` | Сборка `.so`, конфигурация cinterop, подключение `libdl` и упаковка файла в RPM. |
| `composeApp/src/auroraMain/.../platform/NativeInteropProbe.aurora.kt` | Aurora `actual`: подготовка аргументов, вызов C и проверка результата. |
| `composeApp/src/commonMain/.../platform/NativeInteropProbe.kt` | Общий `expect` и описание результата отдельной проверки. |
| `composeApp/src/commonMain/.../ui/AuroraDiagnosticsScreens.kt` | Кнопка, итог и запись результатов в журнал экрана библиотек. |

Для Android, iOS и Desktop сейчас предусмотрены `actual`-заглушки, возвращающие `null`: там этот пример `.so` **не реализован**, и интерфейс сообщает о пропуске. Это не означает, что C Interop на этих платформах не поддерживается в принципе.

## 1. Сборка разделяемой библиотеки

Задачи `buildInteropProbe_aarch64` и `buildInteropProbe_x86_64` запускают соответствующий кросс-компилятор внутри Docker-образа `aurora-build-tools:5.2.1.200`. Исходник компилируется с `-shared -fPIC -O2` в ELF `.so` для выбранной архитектуры. Образ и Docker должны быть доступны локально; требуемая версия образа сейчас **задана в Gradle явно**.

Результат для ARM64:

```text
composeApp/build/native-interop/aarch64/libaurora-interop-probe.so
```

Для x86_64 аналогичный файл находится в `composeApp/build/native-interop/x86_64/`. Пакетные Gradle-задачи зависят от сборки библиотеки своей архитектуры; готовые бинарники не хранятся в исходниках Git.

Пример сборки debug RPM для ARM64 из корня проекта:

```bash
./gradlew -PbuildVariant=aurora :composeApp:buildDebugPackageAuroraArm64 --no-configuration-cache
```

Отдельно скомпилировать `.so` можно задачей `:composeApp:buildInteropProbe_aarch64` или `:composeApp:buildInteropProbe_x86_64`. При этом полученная библиотека должна соответствовать архитектуре, ABI и системным библиотекам целевой Aurora OS: успешная компиляция ещё не гарантирует совместимости со всеми версиями устройств.

## 2. Генерация биндингов cinterop

В `kotlin { ... }` для `auroraArm64` и `auroraX64` создаётся cinterop `interopProbe`. Он читает `.def` и заголовок из `native-interop`; типы и функции становятся доступны Kotlin в пакете `com.example.aurorakmpdemo.interop`. Флаг линковщика `-ldl` нужен обёртке для API динамической загрузки.

Заголовок задаёт C-структуру `InteropProbeResult` и inline-функцию `interop_probe_call`. Kotlin вызывает **обёртку**, а не Kotlin-класс из `.so`. Сигнатуры функции, структуры, версия заголовка и бинарника должны совпадать: Kotlin/Native и загрузчик не гарантируют безопасную диагностику произвольного ABI-расхождения.

## 3. Упаковка и загрузка на устройстве

В `auroraBuild.rpm.extraFiles` описан исходный `.so` для соответствующей архитектуры и путь назначения:

```text
/usr/share/com.example.aurorakmpdemo/lib/libaurora-interop-probe.so
```

На этапе упаковки файл входит в RPM; отдельная ручная установка `.so` не нужна. Установку можно проверить внутри эмулятора:

```bash
rpm -ql com.example.aurorakmpdemo | grep libaurora-interop-probe
file /usr/share/com.example.aurorakmpdemo/lib/libaurora-interop-probe.so
```

Путь загрузки в `interop_probe.h` сейчас **захардкожен** и должен совпадать с путём в `extraFiles`. При смене ID приложения или расположения нужно обновить оба места. Права на файл и доступ к нему в sandbox также необходимо проверить для конкретного профиля. Данный вызов проверялся при запуске `startDebug --nosandbox`; работа в sandbox в рамках этого опыта не подтверждена.

## 4. Вызов и владение памятью

На Aurora `runNativeInteropProbe()` выделяет `InteropProbeResult` и массив `IntVar` внутри `memScoped`, затем передаёт их указатели в `interop_probe_call`. Kotlin-строка передаётся в C как строка UTF-8 с завершающим нулём. C-функция читает аргументы, заполняет предоставленную вызывающей стороной структуру и возвращает код результата.

Обёртка вызывает `dlopen(..., RTLD_NOW | RTLD_LOCAL)`, находит экспорт `aurora_interop_probe` через `dlsym`, выполняет его и закрывает handle через `dlclose`. Значения из структуры читаются Kotlin-кодом **до выхода из `memScoped`**; указатели нельзя сохранять после завершения области. `.so` не должна хранить переданные ей указатели после возврата функции. Строковый буфер результата ограничен 128 байтами вместе с завершающим нулём; неподходящие аргументы функция отклоняет.

Этот пример не передаёт Kotlin-объекты, коллекции или исключения через ABI. Для сложных данных потребовался бы отдельный C-совместимый контракт с явными правилами жизни памяти, ошибок и потоков. Проверка `Char` передаёт одну UTF-16 code unit через `uint16_t`; это не универсальная обработка Unicode-символов из нескольких code units. Встроенный нулевой байт в C-строке завершает строку.

## 5. Что проверяется

На экране **«Проверка библиотек» → «Проверить C Interop»** выполняются 16 проверок:

- знаковые `int8_t`, `int16_t`, `int32_t`, `int64_t` и беззнаковые `uint8_t`, `uint16_t`, `uint32_t`, `uint64_t`;
- `float`, `double`, C `_Bool` и UTF-16 code unit в `uint16_t`;
- строка `char*` в UTF-8, длина в байтах `size_t`, массив `int32_t*` и передача размера;
- числовое значение C enum, переданное в ABI как `int32_t`, указатель `void*`, его идентичность и `null`;
- заполнение структуры результата, полученной от вызывающей стороны.

Функция C выполняет простые операции над значениями, а Kotlin сверяет каждый результат с ожидаемым. Это проверка выбранных примеров, **не исчерпывающий тест всех значений, архитектур, строк, ABI, обратных вызовов или типов C/C++**. Ошибки отдельных проверок и итог показываются на экране и записываются в `library-checks.log`; новый запуск этой или полной проверки перезаписывает предыдущий журнал.

На проверенном эмуляторе Aurora OS 5.2.1.200 ARM64 при запуске с `--nosandbox` получены успешные результаты всех 16 операций. Для x86_64 отдельно подтверждена сборка `.so`, но запуск и Interop-проверка на x86_64 не подтверждены.

## Ошибки и ограничения

- Код `-1` означает, что `dlopen` не загрузил файл; проверьте путь, содержимое RPM, архитектуру, зависимости и права доступа. Подробный текст `dlerror()` текущая обёртка не выводит.
- Код `-2` означает, что `dlsym` не нашёл `aurora_interop_probe`; проверьте экспорт и соответствие версии заголовка и `.so`.
- Код `-3` возвращает функция C при недопустимых указателях или слишком длинной строке; `-4` — при неподдерживаемом значении режима.
- При сборке текущим RPM-инструментом наблюдалось предупреждение `File listed twice` для этой `.so`; ARM64 RPM при этом собрался, установился на dev-эмулятор и содержал библиотеку. Причину предупреждения стоит проверить при изменении упаковщика.
- Debug RPM в проекте не подписан. Обход RPM-проверок допустим только для доверенного пакета на выделенном тестовом эмуляторе; для штатной установки нужна подходящая подпись.
